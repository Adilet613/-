# SÖZ — методология

## Архитектура и воспроизводимость

Чистый JavaScript-модуль engine.js выполняет проверки в браузере и Node.js CLI. UI получает автоматические находки от этого же модуля. Веб-сайт не отправляет ARB на сервер и не вызывает LLM. Шрифты могут загружаться из Google Fonts; при недоступности используются системные шрифты. Внешние запросы за шрифтами не содержат тексты ARB.

## Детекция

| Код | Логика | Ограничение |
|---|---|---|
| untranslated | Нет ключа или пустой перевод непустого исходника | Намеренно пустые ключи задаются allowedBlank |
| same_as_source | NFC и сравнение без учёта регистра | Бренды, числа, токены, allowlist и допустимые термины исключаются; неизвестные имена требуют решения человека |
| placeholder_mismatch | Рекурсивный ICU-парсер, имена аргументов и защищённые теги/токены | Набор токенов защищён; смысл порядка слов проверяет человек |
| plural_mismatch | Типы ICU, число controls, обязательный other, offsets, exact/select branches | Не требует русские few/many в KK. Не заменяет Flutter-компилятор |
| glossary_violation | RU-термин в подписи/фразе и разрешённые KK-варианты | Ограниченное распознавание окончаний; морфология не полная |
| length_overflow | Заданные maxChars или короткие UI-ключи с большим ростом длины | Измеряются символы, а не пиксели. Не гарантия реального clipping |
| machine_translation_suspect | Узкие смысловые правила: противоположная отмена/начало, потеря 24/7, русская конструкция | Сложные кальки и смысловые искажения могут быть пропущены |
| inconsistent_term | Разные переводы одинаковых коротких RU-подписей | Низкий приоритет; разные контексты/падежи могут быть правильными |
| suffix_harmony | Фиксированный аффикс после настоящего простого динамического ICU-аргумента | Правильное окончание для произвольного ника универсально не выбирается |
| orthography | Явные словарные пары и смешение алфавитов внутри слова | Узкое покрытие; не общая проверка правописания |
| wrong_language | Несколько RU/UZ лексических признаков при отсутствии KK-якорей | Имена, цитаты и смешанные тексты требуют контекста |

## Работа с решениями

Начальный статус каждой находки — неподтверждённый. Человек видит source, target, severity и evidence, правит предложение и подтверждает его с именем и временем. Редактирование сбрасывает подтверждение. Ложная находка исключается из финального JSON, но остаётся в журнале. «Нужен контекст» не становится изменением.

При применении проверяются хеши исходных файлов, исходный текст каждой строки, имя, дата и явный флаг reviewed_by_human. Перед записью fixed ARB проверяется структура всех переводов, включая неизменённые. Metadata изменённой строки содержит reviewed_by_human, reviewer, reviewed_at. Неизменённые входные metadata сохраняются. Имя проверяющего — пользовательское заявление, не электронная подпись.

## Метрики и неизвестные

Число находок, распределение и прогресс вычисляются из текущего аудита. Confidence — ручная оценка правила; не калиброванная вероятность. Семантический score и «точность 99%» не показываются. Precision можно измерить на вручную размеченной случайной выборке. Recall скрытых seeded-ошибок измеряет жюри. Искусственный пример не доказывает результат на Grand Mobile.

## Отдельные проверки перед сдачей

Применить к реальным RU/KK, проверить все изменённые строки носителем, измерить precision с описанием выборки и выполнить flutter gen-l10n с фактическим SDK. Идентификаторы не переименовываются автоматически. Если исходный контракт не подходит стандартному Flutter, требуется согласованная миграция шаблона и обращений клиента. Python/JS структурная проверка не является журналом компиляции.

## Дополнительный LLM

Команда propose выбирает ключи из автоматических находок и запрашивает предложения у явно выбранного провайдера. Это улучшение предложений, не самостоятельный полный семантический детектор. Предложения проверяются на структурную сохранность и никогда не отмечаются как просмотренные человеком. Использование и стоимость сохраняются. Для предложений без достаточного контекста модель инструктируется пропускать ключ.
